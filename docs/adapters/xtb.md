# xTB results to QVF

The development version of `qvf-writer` provides `qvf export-xtb` and
`qvf.adapters.xtb.write_xtb`. This companion exporter reads completed
**molecular GFN0/1/2-xTB** output files and writes a new, validated QVF. It
does not run a calculation and does not require xTB, NumPy or a viewer at
export time. It is not present in the released toolkit v0.6.0; install from
a source checkout containing the adapter:

```sh
python -m pip install './python[validate]'
```

## Prepare the calculation

Request xTB's machine-readable output in `xcontrol`:

```text
$write
  json=true
$end
```

For example, run an optimisation in a fresh calculation directory:

```sh
xtb molecule.xyz --gfn 2 --chrg 0 --uhf 0 --input xcontrol --opt --molden --wbo
```

Use the corresponding final geometry, JSON and optional result files from
that same run. The exporter does not search a directory for output files:
explicit paths prevent it from accidentally collecting stale results.
xTB's [property documentation](https://xtb-docs.readthedocs.io/en/latest/properties.html)
describes JSON, Molden and cube requests. It is the source program, not the
exporter, that must produce the quantities requested.

## Export

```sh
qvf export-xtb xtbout.json --geometry xtbopt.xyz --charge 0 \
  --trajectory xtbopt.log --wbo wbo \
  --molden molden.input --spin restricted -o optimisation.qvf
qvf validate optimisation.qvf
```

The geometry can also be a molecular Turbomole `coord` file, including
`xtbopt.coord` when the input used that format. Bare `$coord` coordinates
are bohr; `$coord angs` coordinates are angstrom. `$chrg` and `$spin` on
their header lines are retained. Fractional coordinates, periodic cells,
fixed-atom markers, external file references and other coord data groups
are rejected rather than silently dropped. XYZ must contain exactly one
molecular result geometry. Use `--trajectory` for optimisation frames.

The output must not exist. The exporter validates a temporary archive and
only publishes it after validation succeeds. A failed import does not leave
a partial output or replace an existing file. The JSON report lists imported
sections, limitations, omitted JSON fields and converter/validator findings.

For a Hessian calculation, export `xtbout.json` with the matching geometry
and add `--modes g98.out`. For density or another scalar volume, add one or
more explicit file/quantity pairs:

```sh
qvf export-xtb xtbout.json --geometry molecule.xyz --charge 0 \
  --modes g98.out --cube density.cub volume.density -o frequencies.qvf
```

Only pass these options when those files were generated by that calculation.
The cube quantity is an assertion by the caller; the exporter does not infer
units or physical meaning from a filename. FOD can be carried as
`volume.generic`; it is not relabelled as the total electron density.

## What is preserved

| xTB data | QVF representation |
|---|---|
| Final XYZ or molecular coord | `structure`, angstrom coordinates |
| JSON total energy | Root `energies` and `provenance.scf_energy`, hartree |
| Method/version | Provenance; `source` identifies the exporter |
| Partial charges | `atom_properties.mulliken_charge` for GFN1/2; GFN0's different charge model is labelled `custom.xtb_charge` |
| JSON molecular dipole | Root dipole vector and magnitude in debye |
| `wbo` | Wiberg `bond_orders`, atom indices converted from one-based to zero-based |
| `xtbopt.log` XYZ frames | `trajectory`, angstrom coordinates and hartree frame energies |
| JSON orbital energies/occupations | `provenance.x_xtb`, energies converted from eV to hartree; no orbitals are invented from levels alone |
| Explicit Molden file | `wavefunction.gto` using the existing [Molden conversion contract](../converters.md); explicit spin, real molecular s/p/d subset |
| JSON IR/Raman data | `spectra.ir` / `spectra.raman` and vibrational properties in provenance |
| xTB-generated `g98.out` | `vibrations` with reference geometry and normal-mode displacements |
| Explicit scalar cubes | The requested `volume.*` kind using the existing cube converter |

The JSON's electron count is xTB's **valence** count, recorded as
`provenance.x_xtb.valence_electrons`. It is never subtracted from nuclear
charges to invent molecular charge. Supply `--charge` or use a coord file
with `$chrg`; otherwise charge remains unstated. Multiplicity is one plus
JSON's unpaired-electron count, or an explicit `--multiplicity` when that
field is absent. Contradictory counts, spin, charge sums, array lengths,
duplicate JSON keys and nonfinite mapped values are errors.

Normal modes follow xTB's `g98fake2` output, not a general Gaussian parser.
xTB omits modes with absolute frequency at most 0.1 cm⁻¹ from that file and
rounds displacements to two decimals. The exporter matches the remaining
mode frequencies against JSON, preserves that precision and selects the
corresponding JSON intensities/masses. Dummy zero force constants and Raman
activities in `g98.out` are ignored. Without `--modes`, frequency data and
spectra remain available but there is no animated `vibrations` section.
No Hessian diagonalisation or mode normalisation is performed here.

The xTB adapter removes the primitive normalization already included by
xTB's `printmold` writer and reverses odd-angular-momentum phases: xTB uses
atom-minus-point coordinates, whereas QVF uses point-minus-atom coordinates.
These corrections are specific to xTB; generic Molden conversion is unchanged.
The Cartesian d-component ordering/scaling follows the existing converter.
See [xTB's writer](https://github.com/grimme-lab/xtb/blob/v6.7.1/src/printmold.f90)
and [density evaluator](https://github.com/grimme-lab/xtb/blob/v6.7.1/src/cube.f90).

Molden orbitals retain the `custom` orbital-kind label by default;
the file alone does not distinguish canonical from transformed orbitals.
`--canonical-orbitals` (Python: `canonical_orbitals=True`) explicitly asserts
untransformed canonical xTB orbitals and enables canonical orbital labels in
consumers. The managed runner below establishes that origin automatically.
GFN0 custom charges have a labelled table in current vibe-view development
source; older consumers may not display custom properties. Provenance-only
arrays may not have a dedicated display. All mapped kinds use existing QVF v1 contracts;
no schema or consumer pin changes are needed.

The final trajectory geometry/energy must match the selected geometry/JSON.
Molden, cube and mode-file geometries must match the selected geometry and
atom order within 0.00002 angstrom (to allow text-output rounding). JSON
and `wbo` contain no coordinates: matching dimensions cannot prove that
they came from the same run. The caller must establish that association.

Convergence remains unstated unless `--run-status converged` or
`--run-status failed` is supplied from independent execution evidence.
Successful conversion is not scientific acceptance. The exporter does not
copy the command line, parameter paths, filenames, arbitrary JSON values
or logs into the archive. Unmapped JSON field names are listed in the report.
Atomic multipoles and thermochemical totals currently remain unmapped.

Periodic GFN-FF, g-xTB, PTB, dynamics/scan ensembles whose last frame is not
the selected result, unrestricted formats beyond the Molden converter's
contract and native binary restarts are outside this adapter's current scope.

## Python API

```python
from qvf.adapters.xtb import write_xtb

report = write_xtb(
    "xtbout.json", "xtbopt.xyz", "optimisation.qvf",
    charge=0, trajectory="xtbopt.log", wbo="wbo",
    molden="molden.input", spin="restricted",
)
print(report["sections"])
```

Paths are passed through the API; no subprocess is invoked. Optional
arguments have the same meanings as their command-line counterparts.

## Run and export a queue payload

The development source also provides `qvf run-xtb` and
`qvf.adapters.xtb_run.run_xtb`. Unlike the file exporter, this command executes
the explicitly named xTB binary. It is intended as a local serial queue
payload; it does not submit or schedule work itself:

```sh
qvf run-xtb xtb-job.json --binary /opt/xtb/bin/xtb
```

The request lives beside `coord` and `xcontrol`, which must request JSON and
any selected density output. vibe-view creates all three files. The request
contract is:

```json
{
  "version": 1,
  "method": "GFN2-xTB",
  "task": "optimization",
  "charge": 0,
  "multiplicity": 1,
  "outputs": {"orbitals": true, "bond_orders": true, "density": false},
  "frozen_atoms": []
}
```

Tasks are `single_point`, `optimization` and `frequencies`. `frozen_atoms` is
an optional list of zero-based atom indices, valid only for optimisation;
the corresponding `$fix` input must also be present. The runner checks that
every saved trajectory frame and the final geometry retain those coordinates
within 0.00002 angstrom. A violation refuses acceptance. In xTB 6.7.1, use
`$opt` / `engine=fire` for fixed Cartesian atoms; the default ANC optimiser
can move them. The viewer selects FIRE for these jobs.

The runner creates a new `xtb-results/` directory and never reuses it. It
sets OMP/OpenBLAS/MKL threads to one and streams the engine log while saving
`xtb-results/xtb.out`. A zero exit code, the exact normal-termination message,
absence of `NOT_CONVERGED`, and, for optimisation, `.xtboptok` are required.
Requested output files must exist and pass the exporter checks. Only then
is `result.qvf` published beside the request with converged provenance and
canonical orbital labels. Failure retains diagnostic files and returns a
nonzero exit status; it does not publish a success archive. Existing
`result.qvf` or `xtb-results` paths are refused.

The program must have its own parameters installed. In particular, the
checked xTB 6.7.1 runtime required the external `param_gfn0-xtb.txt` for GFN0;
the exporter does not download or substitute it. GFN0 custom-charge display,
periodic GFN-FF, g-xTB and remote-runtime deployment remain separate concerns.

Real xTB 6.7.1 jobs through vq exercised neutral/ionic/radical results,
optimisation, fixed atoms, Hessians, GFN0/GFN1 and sulfur d orbitals. Density
readback was compared with xTB cubes at sampled grid points. xTB cubes use a
quantized exponential lookup and screening, so they are not an exact-value
reference for the viewer's analytic Gaussian evaluator. Matching the lookup
and disabling density-matrix screening reduced maximum sampled differences
to below 0.000025 atomic units for the checked GFN2 cases. This is bounded
integration evidence, not a chemistry benchmark or an exhaustive element test.
